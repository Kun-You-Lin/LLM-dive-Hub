🌊 現代 RAG 的「三級漏斗」全景架構

傳統幼稚的 RAG（Naive RAG）通常只是簡單地把整份 PDF 切成每 500 字一塊，丟進向量資料庫，問問題時拉出 Top-3 送給 LLM。 在真實世界中，這種做法會頻繁遭遇「檢索噪聲過高、關鍵數字被切斷、LLM 答非所問」的窘境。

現代生產環境採取的標準架構是三級檢索漏斗（Three-Stage Pipeline）：

1. 文本切塊Chunking + Overlap
→
2. 雙路粗篩Vector + BM25
→
3. 混合融合RRF 排名整合
→
4. 精密重排Cross-Encoder Rerank
→
5. 提示裝填LLM Synthesis
💡 為什麼需要「混合檢索（Hybrid Search）」？
• 向量檢索 (Dense Embedding) 擅長捕捉「意圖與近義詞」（如問「電腦好卡」能找到「記憶體不足」）。
• 關鍵字檢索 (BM25 Sparse) 擅長精確命中「特定編號與專有名詞」（如問「產品型號 X1-Pro-2024」或「錯誤碼 0x8004」）。兩者結合才能做到攻守兼備！

💻 混合檢索與 Rerank 實戰代碼 (Python)

from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
from sentence_transformers import CrossEncoder

# 步驟 1: 建立 BM25 關鍵字與向量雙路檢索器
bm25_retriever = BM25Retriever.from_documents(chunks)
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 10})

# 步驟 2: 透過 RRF (Reciprocal Rank Fusion) 進行混合粗篩
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.4, 0.6]
)
initial_docs = hybrid_retriever.invoke(user_query)

# 步驟 3: 使用 Cross-Encoder 精密重排，篩出 Top-3 高價值段落
reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')
pairs = [[user_query, doc.page_content] for doc in initial_docs]
scores = reranker.predict(pairs)

# 依分數排序並選取最高分
ranked_docs = [doc for _, doc in sorted(zip(scores, initial_docs), reverse=True)][:3]

🤔 隨堂思考題

問題 1：既然 Cross-Encoder Reranker 效果這麼好，為什麼不一開始就拿它檢索全庫 100 萬篇文檔？

解答：因為 計算複雜度（Computational Cost） 的巨大差異！
• Bi-Encoder（向量檢索）：可以預先將 100 萬篇文檔離線編碼成向量存入索引。檢索時只需將使用者的提問轉成一個向量，進行點積計算，透過 HNSW 索引幾毫秒即可完成。
• Cross-Encoder（重排器）：必須將「問題」與「段落」拼在一起 [Query, Passage] 共同送入 Transformer 進行全員注意力計算。如果對 100 萬篇文檔全部做 Cross-Encoder，一次檢索可能需要數十分鐘！因此工業界一律採用「雙路粗篩抓出前 50 篇 → Reranker 挑出前 3 篇」的高效架構。

問題 2：切塊大小（Chunk Size）過大或過小，分別會引發什麼問題？

解答：
• 切太小（如 50 字）：語意嚴重斷裂，可能這塊寫著「該伺服器型號為 A100」，下一塊寫著「其功耗為 400W」，檢索時只命中其中一塊，導致 LLM 無法得知這 400W 是屬於哪個型號。
• 切太大（如 2000 字）：單一塊內混雜過多無關雜訊，稀釋了 Embedding 向量的焦點（導致語意不精準），且白白浪費 LLM 的 Context Window 與計算 Token 費用。
